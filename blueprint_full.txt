1. Executive Summary
Autowork.com is a multi-user, multi-organization SaaS platform for authorized email automation. Users connect approved sending accounts, import recipient data, build reusable templates with dynamic variables, and run tracked, queue-based email campaigns with real-time progress reporting.
This document is the pre-development blueprint: it consolidates the frontend build brief and the backend Software Requirements Specification (SRS) into a single reference so that (a) the build can start from a clear, shared structure, (b) any developer joining later can onboard quickly, and (c) the client has a plain-language document to review and sign off on before implementation begins.
The single most important open item — the identity of the real email provider(s) — is called out separately in Section 11 and must be confirmed by the client before the real provider adapter is built. Development starts with a fake/test provider so frontend, backend, queues and workflows can all be built and demoed in parallel.
Update (v1.1): the client has confirmed that attachment storage will use the pCloud API. The pCloud adapter should be built now, wired through the same pluggable storage-service interface described in Section 4, and configured entirely through environment variables. The client will send the actual pCloud API keys separately once the rest of the platform is complete — until the keys arrive, the adapter runs against placeholder/env-based credentials so nothing is hard-coded or blocked. See Section 11 for the exact current status of every confirmation item.
2. Project Overview
Product: authorized, multi-tenant email automation platform (not a spam tool — every send goes through an authorized, connected sending account).
Frontend: Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui, desktop-first, inspired visually (not functionally or in branding) by pCloud's clean SaaS file-management UI.
Backend: Node.js + NestJS + PostgreSQL (via Prisma) + Redis/BullMQ for background job processing.
Core loop: Login → Connect account(s) → Import contacts → Build template → (optional) Attach files → Build campaign → Launch → Background workers send → Live progress + logs.
Multi-tenant from day one: every resource is scoped to an organization; users and roles sit inside an organization.
3. Objectives
Ship a production-structured platform (not a throwaway prototype) with a clean separation between frontend, backend, and the email-provider adapter layer.
Keep the email-sending provider abstracted behind an adapter interface so the real provider can be swapped in later without reworking the UI or the campaign/queue logic.
Support multiple authorized sending accounts per organization, with safe account selection that respects provider limits.
Give users full visibility into campaign progress and results in real time, without needing to refresh the page.
Produce documentation and a folder structure clear enough that a new developer can be productive within a day.
4. Scope of Work — v1
4.1 In scope
Authentication (register, login, forgot/reset password), protected routes, RBAC (user vs. admin).
Organization-based multi-tenancy.
Email account connection UI + backend record-keeping (Connect / Validate / Disconnect / Disable / Delete) — provider-agnostic.
Contacts and contact lists, with CSV / XLSX / TXT / paste import (upload → preview → column mapping → validation → duplicate detection → confirm).
Template manager with dynamic variables (#NAME#, #FIRSTNAME#, #LASTNAME#, #EMAIL#, #PHONE#, #COMPANY#, #RANDOM#) and live preview against sample data.
Optional attachments, stored via a pluggable storage service. CONFIRMED: the storage provider is pCloud, integrated via the pCloud API — built behind the same adapter interface so credentials are the only thing that changes when the client sends its API keys.
Multi-step campaign builder (details → accounts → recipients → template → attachments → configuration → review → launch).
Campaign monitoring: list view, detail view, progress bar, live counts (queued / processing / sent / failed / retrying).
Real-time updates via Socket.IO / WebSockets (job.completed, job.failed, campaign.updated, campaign.completed).
Automation registry (selectable automations; admin can manage definitions).
Logs (campaign logs, execution logs, errors) with search, filters and date range.
Settings (profile, organization, security, notifications) and an Admin Panel (users, organizations, automations, campaigns, system logs, queue/worker health, provider configuration status).
Swagger/OpenAPI documentation for all backend endpoints; Dockerized local development.
4.2 Explicitly out of scope for v1 (until confirmed)
The real email-sending provider adapter (Gmail / Microsoft 365 / SMTP / other) — built only after client confirmation. A fake/test provider stands in until then.
Live pCloud connectivity — the adapter and integration code are built now, but cannot be tested end-to-end until the client sends the real pCloud API keys.
Advanced sending-limit / anti-spam rule tuning specific to a provider, since those rules depend on which provider is confirmed.

├── frontend/                 Next.js app (App Router)

│       logs, admin, common, config
├── automation-modules/email/  Provider-agnostic email adapter interface
│   └── providers/             gmail.adapter.ts, microsoft.adapter.ts, smtp.adapter.ts (added once confirmed)
├── workers/                    email.worker.ts, import.worker.ts, campaign.worker.ts

├── docker/                     Dockerfile.frontend, Dockerfile.backend, docker-compose.yml
└── docs/, .env.example, .gitignore, README.md
Frontend and backend each keep a clean service layer: the frontend never scatters raw fetch/axios calls inside components (everything goes through src/services/*), and the backend never sends real emails synchronously inside an HTTP request — sends only happen through the Redis/BullMQ queue and a worker.
7. High-Level Workflow
7.1 User journey
Login → Dashboard → Connect authorized email account(s) → Import contacts (CSV/Excel/TXT/paste) → Preview & validate → Create template → Insert variables (#NAME#, #COMPANY#, #RANDOM#, …) → Optional attachment → Create campaign → Select account(s) → Review → Start → Live progress → Logs/report.
7.2 System / execution flow
NestJS API creates jobs → Redis/BullMQ queue → Email Worker picks up job → selects an eligible sending account → loads recipient → resolves variables → builds subject/body → loads attachment → calls the Provider Adapter → sends → records the result → updates campaign counters → moves to the next job → campaign completes → results are written to logs and pushed to the UI in real time.

12. Security Principles
No secrets (OAuth secrets, API keys, refresh tokens, SMTP passwords) ever ship in frontend source code or logs.
Access tokens, refresh tokens, passwords and other secrets are never displayed in the UI.
HTTPS, secure sessions/tokens, password hashing, RBAC, tenant isolation, encrypted provider credentials, file validation, upload limits, rate limiting, audit logs and secure headers throughout.
13. Definition of Done
The core platform is considered done when authentication, tenant isolation, dashboard, accounts, contacts/imports, templates, attachments, campaigns, queue infrastructure, logs, admin and the required APIs are implemented, tested and connected end-to-end. The email integration itself is only considered done once the client-approved provider is confirmed, account connection works, jobs process correctly, variables and attachments resolve correctly, results are recorded, provider rules are respected, acceptance tests pass, and documentation is updated.
